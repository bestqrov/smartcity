# العمارة الأمامية لتطبيق التعليم (`apps/education-app`)

> تبني هذه الوثيقة على واقع `tourism-app` التقني الفعلي (مُدقَّق سابقًا: Next.js 15 App Router، React 19، Tailwind، بنية `src/app/[locale]/...`، `src/lib/api.ts` عبر gateway، Context للمصادقة). `education-app` تتبع **نفس النمط التقني حرفيًا**، مع تصحيح الفجوة الوحيدة المرصودة في Tourism (عدم استعمال `@smartcity/ui`) منذ البداية.

---

## 1–2. فلسفة ومبادئ الفرونت إند

نفس فلسفة الخلفية (Prompt 07، القسم 1): تكرار نمط ناجح ومُختبر (`tourism-app`) بدل ابتكار بنية جديدة. الفارق الوحيد المقصود: تبني `@smartcity/ui` الكامل، ومصادقة عبر تحقق من جانب الخادم بدل الاكتفاء بتحقق العميل.

## 3. عمارة التطبيق

Next.js App Router، بنية `src/app/[locale]/(role-group)/...` مطابقة لنمط route groups الحالي في `tourism-app` (`(guest)`, `admin`, `bookings`...) لكن منظَّمة حول الأدوار الأساسية لـ Education: `(admin)` للإدارة التنفيذية، `(teacher)`, `(student-parent-portal)` كمساحة بوابة ذاتية منفصلة بصريًا (Prompt 06، القسم 3).

## 4. استراتيجية تنظيم المجلدات

`src/app/[locale]/*` للصفحات (Routing)، `src/components/*` منظَّمة حسب **الوحدة الوظيفية** لا بشكل مسطَّح (`components/students/`, `components/finance/`, `components/academic/`...) — تحسين مقصود عن نمط `tourism-app` المسطَّح الحالي، مبرَّر بعدد الوحدات الأكبر في Education (Prompt 05: 16 وحدة جوهرية مقابل نطاق أضيق في Tourism). `src/lib/*` لمنطق عابر (api.ts, auth.tsx, i18n.ts، بنفس الأسماء والنمط الحالي في `tourism-app` لتقليل الاحتكاك المعرفي بين الفريقين).

## 5. البنية القائمة على الميزات (Feature-Based)

كل مجلد `components/<module>` يحوي مكوّناته الخاصة + أي منطق عرض خاص بذلك الدومين (مثال: `components/attendance/AttendanceSheet.tsx`)، بمعزل عن مكوّنات UI العامة المستوردة من `@smartcity/ui`.

## 6. استراتيجية المكوّنات المشتركة

قاعدة صارمة وغير قابلة للتفاوض (تصحيح الفجوة المرصودة في Tourism): **أي حاجة لزر/حقل/بطاقة/شارة/نافذة حوار تُستورَد من `@smartcity/ui` أولاً**؛ لا يُنشأ مكوّن محلي مطابق إلا إذا أثبت الفريق فعليًا أن الحاجة غير مغطاة، وعندها يُضاف المكوّن الجديد إلى `@smartcity/ui` نفسها (مساهمة في الحزمة المشتركة)، لا كنسخة محلية داخل `education-app` فقط.

## 7–8. تنظيم مكوّنات الواجهة والأعمال

مكوّنات UI عامة (من `@smartcity/ui`) مقابل مكوّنات أعمال (Business Components، خاصة بمنطق Education — مثل `StudentCard`, `InvoiceStatusBadge` المبني فوق `Badge` العام). الفصل بينهما هو نفس الفصل المحدَّد في Prompt 06 (عمارة المكوّنات).

## 9. عمارة التخطيط (Layout)

`ClientLayout`/`Providers` بنفس نمط `tourism-app` الحالي، مع إضافة طبقة "سياق الدور" (Role Context) تحدد القائمة الجانبية والصلاحيات المعروضة بناءً على الدور والوحدات المفعّلة (Prompt 06، القسم 5).

## 10–11. عمارة التوجيه واستراتيجية التنقل

Next.js App Router مع Middleware لإعادة توجيه اللغة (بنفس `src/middleware.ts` الحالي في `tourism-app`)، بالإضافة إلى **حماية توجيه من جانب الخادم** للمسارات المحمية (تحسين عن Tourism الحالية التي تعتمد فقط على تحقق من جانب العميل) — قرار مثبَّت في Prompt 03 (القسم 14، البند 2).

## 12. استراتيجية إدارة الحالة

**React Query (TanStack Query) لحالة الخادم** (بيانات الطلبة، الفواتير، الجداول...)، بدل الاعتماد على `useState`/`useEffect` يدويًا كما في `tourism-app` الحالية — تحسين مقصود ومبرَّر بحجم البيانات وتعدد الوحدات في Education (16 وحدة جوهرية تحتاج تخزينًا مؤقتًا وإعادة جلب ذكية، بخلاف نطاق Tourism الأضيق). **Context بسيط لحالة العميل العابرة** (الدور الحالي، الفرع المختار)، بنفس نمط `AuthProvider` الحالي.

## 13–14. استراتيجيتا حالة الخادم والعميل

- **حالة الخادم**: React Query، مع إعادة تحقق ذكية (Stale-while-revalidate) للوحات القيادة، وتحديث فوري (Invalidation) بعد أي عملية كتابة (تسجيل حضور، إصدار فاتورة).
- **حالة العميل**: محدودة عمدًا (فلاتر مؤقتة، حالة نموذج مفتوح)، بلا مكتبة إدارة حالة عامة إضافية (Redux/Zustand) — غير مبرَّرة لحجم الحالة العميلة الفعلي المتوقع.

## 15–16. استراتيجيتا النماذج والتحقق

React Hook Form + Zod (التوجه التقني العام للمنصة بالكامل)، مع مخططات تحقق (Zod Schemas) مطابقة تمامًا لقواعد Validation المعرَّفة خلفيًا (Prompt 07، القسم 15) لتفادي ازدواجية منطق تحقق متضارب بين الواجهة والخلفية.

## 17–18. تدفق المصادقة ومعالجة التفويض

تسجيل الدخول عبر `education-app` يستدعي `user-service` عبر `gateway` (Prompt 03، القسم 14)، مع تخزين آمن للتوكن (تفضيل HttpOnly Cookie عبر Route Handler من جانب الخادم على تخزين `localStorage` المستعمل حاليًا في `tourism-app` — تحسين أمني مقصود يُفصَّل معياره الكامل في Prompt 10، لا إلزام فوري على Tourism بالتغيير).

## 19. العرض القائم على الصلاحية

عناصر واجهة (أزرار، روابط، أقسام كاملة) تُعرض/تُخفى بناءً على صلاحيات الدور المستخرجة من التوكن، مطابقة تمامًا لقاعدة "الإخفاء الكامل لا التعطيل الرمادي" (Prompt 06، القسم 5).

## 20. استراتيجية Feature Flags على مستوى الواجهة

الوحدات المفعّلة لكل مؤسسة (Prompt 01، القسم 9) تُحمَّل مع بيانات الجلسة عند الدخول، وتتحكم فعليًا في القائمة الجانبية والمسارات المتاحة — لا شرط `if` متناثر في كل صفحة، بل طبقة تصفية مركزية واحدة عند بناء التنقل.

## 21. استراتيجية واجهة متعددة المستأجرين

مؤشر المؤسسة/الفرع الحالي في الترويسة (Prompt 06، القسم 25)، مع كل طلب API يحمل ضمنيًا سياق `tenantId` عبر التوكن، لا عبر معامل يدوي قابل للتلاعب من جهة العميل.

## 22–23. استراتيجيتا التدويل و RTL

`packages/i18n` بنفس نمط `tourism-app` الحالي (`getDirection`, `supportedLocales`)، مع namespace `education` (Prompt 06، القسم 14). RTL أصيل بامتداد كل مكوّنات `@smartcity/ui` (شرط قبول مثبَّت في Prompt 06).

## 24. استراتيجية الاستجابة

Tailwind breakpoints قياسية من `packages/config`، مع قاعدة الجداول→بطاقات على الشاشات الصغيرة (Prompt 06، القسم 12).

## 25. استراتيجية إمكانية الوصول

مطابقة لـ Prompt 06 (القسم 15)، منفَّذة عبر مكوّنات `@smartcity/ui` المتوافقة أصلاً + انتباه إضافي للنماذج الطويلة (تسجيل طالب، إدخال نتائج جماعي).

## 26–27. استراتيجيتا Offline و PWA

غير أولوية للنسخة الويب الأولى (Prompt 06، القسم 17) — تُترك لتطبيق الموبايل (Prompt 09). لا PWA كاملة في هذه المرحلة، يُعاد التقييم إن أثبتت الحاجة الفعلية لاستخدام الويب من أجهزة ميدانية بدون تطبيق مخصص.

## 28. استراتيجية التحديثات اللحظية

Polling خفيف عبر React Query (`refetchInterval`) للإشعارات والعدادات، بدل WebSocket كامل في النسخة الأولى (مطابقة لقرار Prompt 07، القسم "الميزات اللحظية").

## 29. استراتيجية الإشعارات

مركز إشعارات داخل التطبيق (جرس + قائمة)، يستهلك نفس بيانات `MessageLog`/الإشعارات الداخلية المعرَّفة خلفيًا (Prompt 04).

## 30. استراتيجية تجربة البحث

بحث عابر للوحدات في الترويسة (Prompt 06، القسم 22)، منفَّذ كنداء API مؤجَّل (Debounced) لا بحث محلي في المتصفح.

## 31. استراتيجية تفاعل AI

مكوّنات AI (توصيات، مساعد محادثي) معزولة بصريًا وبرمجيًا (مكوّنات `AI*` منفصلة) بحيث يسهل تعطيلها بالكامل عبر Feature Flag دون التأثير على بقية الواجهة، لأنها الأكثر عرضة للتغيّر والتجريب.

## 32–33. استراتيجيتا حدود الخطأ والتحميل

Error Boundaries على مستوى كل مجموعة مسارات (Route Group) لمنع انهيار كامل الصفحة عند خطأ في وحدة واحدة، مكوّنات `Loading`/`Skeleton` من `@smartcity/ui` لكل حالة تحميل بيانات عبر React Query.

## 34. استراتيجية حالة الفراغ

مطابقة لـ Prompt 06 (القسم 21)، منفَّذة كمكوّن `EmptyState` عام قابل لإعادة الاستخدام عبر كل الوحدات (يُقترح كمساهمة جديدة في `@smartcity/ui` إن لم يكن موجودًا).

## 35. استراتيجية التخزين المؤقت (جهة العميل)

React Query cache كطبقة وحيدة لتخزين حالة الخادم مؤقتًا من جهة العميل — لا طبقة تخزين إضافية متوازية.

## 36–37. استراتيجيتا تحسين الأداء والأمان

Code splitting تلقائي عبر Next.js App Router (افتراضي)، تحميل كسول (Lazy Loading) للوحدات الثقيلة (تقارير، تحليلات). أمان الواجهة (XSS, تخزين حساس) محال بالكامل لـ Prompt 10.

## 38. استراتيجية المراقبة والتحليلات (جهة الواجهة)

تُدمَج مستقبلاً ضمن أي حل مراقبة أمامي موجود على مستوى المنظومة (إن وُجد)، بلا حل منفصل خاص بـ Education.

## 39. استراتيجية التسجيل (جهة الواجهة)

تسجيل أخطاء العميل (Console/Error reporting) بنفس أي أداة معتمدة حاليًا على مستوى المنصة، أو تأجيلها كتحسين لاحق غير حرج.

## 40. استراتيجية قابلية التوسع المستقبلية

بنية `src/components/<module>` وReact Query كطبقة حالة خادم موحَّدة تجعل إضافة وحدة جديدة (مثال: تفعيل "المكتبة" لاحقًا) مسألة إضافة مجلد ومجموعة hooks جديدة، بلا إعادة هيكلة الأساس.

## عمارة الصفحات (Page Architecture)

لوحة قيادة (مختلفة لكل دور، Prompt 06)، صفحات CRUD موحَّدة النمط (قائمة/تفاصيل/إنشاء/تعديل)، صفحات معالج (Wizard) للإعداد الأولي وتسجيل طالب جديد الطويل، تقارير وتحليلات، تقويم (جدول زمني)، إعدادات مبوَّبة، مصادقة (دخول/دعوة/استرجاع كلمة مرور)، إدارة (مؤسسة/فروع)، ملف شخصي، بحث، مساحة AI.

## عمارة المكوّنات — فئات مرجعية

تخطيطات، تنقل (Sidebar/Header/Footer)، بطاقات، نماذج، حقول إدخال، جداول، رسوم بيانية، فلاتر، نوافذ حوار/أدراج/تبويبات/أكورديون، خط زمني (Timeline، لعرض تاريخ الطالب — Prompt 04 القسم 17)، إشعارات، مكوّنات وسائط ورفع ملفات، مكوّنات AI — لكل فئة عند التنفيذ الفعلي: الغرض، المسؤوليات، الأنماط، قواعد التركيب، إدارة الحالة الخاصة بها، قواعد الوصول، الاستجابة، RTL، سلوك التحقق والتحميل والخطأ، الامتدادات المستقبلية (نفس إطار Prompt 06).

## الوحدات الأمامية — لكل وحدة عند التنفيذ

المسؤوليات، الصفحات المطلوبة، المكوّنات المطلوبة، المكوّنات المشتركة المستهلَكة، الصفحات المحمية، الصلاحيات، التبعيات، تدفق البيانات، سلوك Offline، سلوك اللحظية، تكامل AI — يُملأ فعليًا لكل وحدة من Prompt 05 عند بدء تنفيذها، بنفس منطق تأجيل التكرار النظري المتبع في Prompt 07.

## تدفق بيانات الواجهة

استهلاك API عبر `src/lib/api.ts` (نفس نمط `tourism-app`، موجَّه لـ gateway)، تخزين مؤقت وتحديث ذكي عبر React Query، تحديثات متفائلة (Optimistic Updates) للعمليات السريعة منخفضة المخاطر (تسجيل حضور)، لا للعمليات المالية الحساسة (تنتظر تأكيد الخادم دائمًا). ترقيم، فلترة، فرز، بحث عبر معاملات API موحَّدة (`IPaginationQuery`). تحميل كسول وتمرير لانهائي للقوائم الطويلة (سجلات حضور، فواتير تاريخية).

## الأمان (جهة الواجهة) — إحالة

مطابقة لـ Prompt 10 بالكامل (مصادقة، تفويض، انتهاء جلسة، تجديد توكن، تخزين آمن، حماية XSS، جاهزية CSRF).

## معايير الجودة

تنظيم كود متّسق مع `tourism-app` الحالي (نفس اصطلاحات التسمية)، إعادة استخدام صارمة عبر `@smartcity/ui` (معيار قبول لكل Pull Request)، أداء (تفادي إعادة رندر غير ضرورية عبر React Query + تقسيم مكوّنات معقول)، إمكانية وصول أساسية، قابلية صيانة (فصل واضح UI/Business components)، جاهزية اختبار (بنية تسمح بفصل منطق عن عرض دون إلزام بكتابة اختبارات في هذه الوثيقة).
