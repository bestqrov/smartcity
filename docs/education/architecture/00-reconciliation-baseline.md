# خط الأساس المعماري النهائي لقطاع Education

> وفق بروتوكول التنفيذ المحدَّد في الوثيقة المرجعية الأصلية: قبل أي تنفيذ فعلي، يجب رصد التناقضات، المتطلبات الناقصة، تكرار المسؤوليات، والمخاطر المعمارية عبر الوثائق العشر (01–10)، ثم إثبات خط أساس واحد. هذا الفحص أُجري عبر كل الوثائق؛ لم تُرصد تناقضات جوهرية، لأن كل وثيقة كُتبت بالبناء الصريح فوق سابقتها مع إحالات متبادلة. النتائج أدناه.

---

## 1. فحص الاتساق — لا تناقضات جوهرية مرصودة

- **الهوية**: Prompt 03 (القسم 14) يحسم الاعتماد على `user-service` عبر `gateway`؛ Prompt 07 (المصادقة)، Prompt 08 (القسم 17–18)، Prompt 09 (القسم 9)، Prompt 10 (القسم 4) كلها تبني على نفس القرار دون تعارض.
- **العزل**: Prompt 04 (القسم 3) يحسم العزل المنطقي بـ `tenantId`؛ Prompt 07 (القسم 13)، Prompt 10 (القسم 3) يترجمانه لطبقة تقنية وأمنية متسقة.
- **الأحداث**: Prompt 03 (القسم 9–10) يحسم غياب Message Broker؛ Prompt 07 (القسم 11)، Prompt 09 (القسم 16) يلتزمان بنفس القرار.
- **AI**: Prompt 03 (القسم 26) يقترح بوابة مشتركة على مستوى SmartCity؛ Prompt 07 (القسم 22)، Prompt 10 (القسم 15) متّسقان معه، مع مسار بديل موثَّق إن لم تكن البوابة المشتركة جاهزة.
- **UI**: Prompt 06 وPrompt 08 متّسقان تمامًا حول تبني `@smartcity/ui` الكامل منذ البداية.

## 2. فجوة تسمية بسيطة — بلا تأثير معماري

Prompt 05 (المواصفات الوظيفية) يُفصِّل "البرامج/المواد/المستويات/الأفواج" كأربع وحدات مستقلة؛ Prompt 07 (الوحدات النطاقية الخلفية) يجمعها في وحدة NestJS واحدة `academic-structure`. هذا **تفصيل تنظيمي للكود لا تناقض وظيفي** — الوحدات الأربع تبقى منفصلة كنماذج بيانات ومنطق (Prompt 04)، فقط مُجمَّعة في مجلد خلفي واحد لتقليل التجزئة. لا حاجة لتعديل أي وثيقة.

## 3. مخاطرة معمارية مقبولة ومسجَّلة (لا حاجز تنفيذ)

`JWT_SECRET` مشترك عبر كل الخدمات الحالية (Prompt 10، القسم 23) — Education ترث هذا النمط بدل حظر البدء. مسجَّلة كتوصية تحسين مستقبلي عابرة لكل SmartCity، خارج نطاق Education وحدها.

## 4. قرارات منتجية معلَّقة (وليست معمارية) — تحتاج حسمًا مع صاحب المشروع عند التنفيذ الفعلي، لا الآن

- القيم الدقيقة لسياسة الاحتفاظ بالبيانات بعد إلغاء مؤسسة (Prompt 04، القسم 35؛ Prompt 10، القسم 21).
- أهداف RPO/RTO الدقيقة للنسخ الاحتياطي (Prompt 10، القسم 22).
- الهوية اللونية النهائية لـ `education-app` (Prompt 06، القسم 1 — اقتراح مبدئي أخضر/أزرق فقط).
- حالة `notification-service` الفعلية عند بدء التنفيذ (تحدد أي مسار من القسم 13/Prompt 03 يُعتمد).
- توفر حل تخزين ملفات مشترك فعلي على مستوى SmartCity (Prompt 03، القسم 23).

هذه القرارات **لا تمنع بدء التنفيذ** — الوثائق صمَّمت مسارات بديلة قابلة للاستبدال لاحقًا دون كسر التوافق (مبدأ "واجهة ثابتة، تنفيذ داخلي قابل للاستبدال" المتكرر عبر Prompt 07).

## 5. أولوية التنفيذ الموصى بها (مستخلصة من Prompt 01 القسم 21 وPrompt 05)

**الدفعة الأولى (MVP)**: المصادقة (استهلاك `user-service`)، إدارة المؤسسة والفروع، إدارة الطلبة، إدارة الأولياء، البرامج/المواد/المستويات/الأفواج، الجدول الزمني، الحضور، الفوترة/الأداءات/الأقساط. هذه الوحدات الثمانية تُشكِّل أصغر منتج ممكن يقدّم قيمة فعلية كاملة (تسجيل طالب → حضور → فاتورة).

**الدفعة الثانية**: الامتحانات/النتائج/الشهادات، إدارة الأساتذة/HR/الرواتب، CRM، التواصل، المستندات.

**الدفعة الثالثة**: التحليلات وAI، الوحدات الاختيارية (مكتبة، مخزون، نقل)، تطبيق الموبايل.

## 6. حالة الأمان الدنيا الإلزامية قبل أي بيانات حقيقية (من Prompt 10، القسم 30)

عزل مستأجر مُختبر بصرامة، مصادقة/تفويض كاملان، تدقيق للعمليات الحساسة، تشفير قياسي، سياسة أسرار سليمة — هذه الخمسة **شرط مسبق** لأي بيئة تحتوي بيانات مؤسسة حقيقية، بغض النظر عن ترتيب بناء الوحدات الوظيفية.

**الخلاصة**: الوثائق العشر متّسقة، خط الأساس معتمد. الانتقال التالي هو التخطيط التنفيذي الفعلي (خطة عمل، لا وثيقة معمارية إضافية) للدفعة الأولى المحدَّدة في القسم 5.
