# عمارة تطبيق الموبايل لقطاع التعليم

> **ملاحظة سياقية مهمة**: خلافًا لـ `education-app` (الويب) التي تكرّر نمطًا تقنيًا موجود فعلاً (`tourism-app`)، **لا يوجد حاليًا أي تطبيق موبايل Flutter ضمن منظومة SmartCity** — هذه أول بنية موبايل للمنظومة ككل. القرارات هنا يجب أن تُصمَّم بحيث تصلح كنمط مرجعي لأي قطاع آخر يبني تطبيق موبايل مستقبلاً (بما فيه Tourism لاحقًا)، لا كحل خاص بـ Education وحدها فقط من حيث الاتصال بالخلفية (`gateway`, JWT, `IApiResponse`) — أما المنطق التجاري داخل التطبيق فيبقى خاصًا بـ Education حصرًا.

---

## 1–3. الرؤية والاستراتيجية والفلسفة

تطبيق موبايل ليس نسخة مصغَّرة من الويب، بل أداة ميدانية سريعة لمهام محدَّدة عالية التكرار: تسجيل حضور، إشعار فوري لولي، اطلاع سريع لطالب. الأولوية: **السرعة والموثوقية في ظروف شبكية ضعيفة**، لا تغطية وظيفية كاملة مطابقة للويب.

## 4. طبقات التطبيق

عرض (Widgets/Screens) → إدارة حالة (State Management) → مستودعات بيانات (Repositories، تجمع بين مصدر محلي ومصدر عن بُعد) → مصدر بيانات محلي (Local Storage/DB) ومصدر بيانات عن بُعد (API Client عبر gateway، نفس الخلفية المستعملة من الويب).

## 5. عمارة قائمة على الميزات (Feature-based)

تنظيم حسب التطبيقات المستقلة (Section التالي)، وداخل كل تطبيق حسب الوحدة الوظيفية (حضور، إشعارات، ملف شخصي)، بنفس منطق تنظيم `education-app` (Prompt 08، القسم 4–5) لتقليل الفجوة المعرفية بين فرق الويب والموبايل.

## 6. النواة المشتركة للموبايل (Shared Mobile Core)

طبقة مشتركة عبر كل تطبيقات الموبايل الست (Section التالي): عميل API (نفس عقود `IApiResponse`/`IApiError` المستعملة في الويب)، طبقة مصادقة، طبقة تخزين آمن، طبقة إشعارات دفع، طبقة تدويل/RTL — **مصمَّمة كحزمة Dart قابلة لإعادة الاستخدام مستقبلاً من قطاعات أخرى**، لا مكرَّرة داخل كل تطبيق.

## 7. تنظيم الوحدات

كل وحدة وظيفية (حضور، إشعارات، ملف شخصي، فواتير) = مجلد Feature مستقل داخل التطبيق المعني، بحدود واضحة مطابقة لتقسيم Prompt 05.

## 8. عمارة التنقل

تنقل بتبويبات سفلية (Bottom Navigation) لكل تطبيق، مطابقًا لتوصية UX (Prompt 06: "نموذج تنقل مبسّط، تبويبات سفلية لا قائمة جانبية").

## 9. استراتيجية المصادقة

نفس تدفق المصادقة المركزي عبر `user-service`/`gateway` (Prompt 03، القسم 14) — **لا نظام مصادقة منفصل للموبايل**. الفارق الوحيد: تخزين التوكن عبر تخزين آمن للجهاز (Secure Storage/Keychain)، لا عبر آلية الويب (Cookie/localStorage).

## 10. استراتيجية التفويض

نفس RBAC الخلفي (Prompt 07)، الواجهة تعرض فقط ما يخص دور المستخدم، بنفس مبدأ الإخفاء الكامل (Prompt 06، القسم 5).

## 11. استراتيجية Offline-first

**الأولوية المعمارية الأهم لكامل هذه الوثيقة**، خصوصًا لتسجيل الحضور (Prompt 02، Prompt 03 القسم 32، Prompt 06 القسم 17 — كل الوثائق السابقة أحالت هذا التفصيل هنا). الآلية: كل عملية كتابة حرجة ميدانيًا (تسجيل حضور) تُكتب أولاً في قائمة انتظار محلية (Local Queue) بغض النظر عن حالة الاتصال، ثم تُزامَن مع الخادم عند توفر الشبكة. المستخدم لا ينتظر الشبكة لإكمال عمله.

## 12. استراتيجية المزامنة

مزامنة تلقائية في الخلفية عند استعادة الاتصال، بترتيب زمني (الأقدم أولاً)، مع إشعار بصري بسيط لحالة المزامنة (قيد الانتظار/تمت/فشلت) بلا إزعاج المستخدم بتفاصيل تقنية.

## 13. استراتيجية التخزين المحلي

قاعدة بيانات محلية خفيفة (مثل SQLite عبر حزمة Flutter قياسية) لتخزين: قائمة انتظار المزامنة، نسخة مؤقتة من بيانات ضرورية للعمل دون اتصال (قائمة طلبة المجموعة الحالية لغرض تسجيل الحضور تحديدًا)، لا تخزين شامل لكامل بيانات المؤسسة محليًا.

## 14. استراتيجية إدارة الحالة

مكافئ Flutter لنمط React Query المعتمد في الويب (Prompt 08، القسم 12): حالة خادم مُدارة عبر طبقة تجريد موحَّدة (Repository + Cache)، حالة عميل محلية بسيطة (Provider/Riverpod أو ما يعادله حسب اختيار الفريق التقني عند التنفيذ — القرار الدقيق لأداة إدارة الحالة يُترك لمرحلة التنفيذ، المبدأ المعماري هو الفصل بين حالة الخادم وحالة العميل).

## 15. استراتيجية استهلاك API

نفس عقود API المعرَّفة خلفيًا (Prompt 07) عبر `gateway`، بلا تفريعة API خاصة بالموبايل — عقد واحد يخدم الويب والموبايل معًا.

## 16. استراتيجية WebSocket

اختيارية، تُفعَّل فقط عند حاجة فعلية لتحديث لحظي حقيقي (مثال: إشعار فوري للولي أثناء استخدامه التطبيق) — تُبنى فوق نفس قرار Prompt 07 (الميزات اللحظية اختيارية في النسخة الأولى)، لا كأولوية بناء أولى.

## 17. استراتيجية الإشعارات الفورية (Push)

Firebase Cloud Messaging كقناة رئيسية (مطابقة للتوجه التقني العام)، مُشغَّلة من أحداث الخلفية نفسها (Prompt 07: `attendance.recorded`, `payment.overdue`...) عبر نفس مسار الإشعارات الموحَّد، لا مسار منفصل خاص بالموبايل فقط.

## 18. استراتيجية المزامنة الخلفية

مهام مزامنة دورية خفيفة حتى مع التطبيق مغلقًا جزئيًا (Background Fetch محدود حسب قيود نظام التشغيل)، لضمان عدم تراكم قائمة انتظار كبيرة دون علم المستخدم.

## 19–20. استراتيجيتا رفع وتنزيل الملفات

رفع مؤجَّل (Queued Upload) لأي ملف يُرفع دون اتصال (مثال: صورة مستند طالب)، بنفس آلية قائمة الانتظار المحلية (Section 11). التنزيل عند الطلب مع تخزين مؤقت محدود المساحة.

## 21. استراتيجية معالجة الوسائط

أساسية (ضغط صورة بسيط قبل الرفع لتوفير البيانات)، بلا معالجة فيديو/صوت متقدمة في النسخة الأولى.

## 22. استراتيجية الروابط العميقة (Deep Links)

روابط لفتح شاشة محدَّدة مباشرة من إشعار (مثال: إشعار غياب يفتح شاشة تفاصيل الحضور مباشرة)، بصيغة موحَّدة عبر كل تطبيقات الموبايل الست.

## 23. استراتيجية الأمان

مطابقة تمامًا لـ Prompt 10: تخزين آمن للتوكن، عدم تخزين بيانات حساسة غير مشفَّرة محليًا، انتهاء جلسة عند خمول طويل للأدوار الإدارية.

## 24–26. استراتيجيات الأداء وتحسين البطارية والشبكة

تقليل نداءات API المتكررة عبر التخزين المؤقت المحلي، تجميع عمليات المزامنة بدل إرسال كل عملية فور حدوثها، تفادي استطلاع دوري (Polling) عالي التردد يستنزف البطارية — الاعتماد على Push بدل Polling كلما أمكن.

## 27–28. استراتيجيتا إمكانية الوصول و RTL

نفس مبادئ Prompt 06 (القسم 13، 15)، منفَّذة عبر دعم Flutter الأصلي لـ `Directionality` — العربية RTL افتراضية.

## 29. استراتيجية التدويل

نفس محتوى `packages/i18n` (namespace `education`)، مُعاد استخدامه أو مُعاد توليده بصيغة تناسب Flutter (ملفات ARB أو ما يعادلها)، مع مصدر حقيقة نصوص واحد منطقيًا حتى لو اختلفت الصيغة التقنية بين الويب والموبايل.

## 30. استراتيجية معالجة الأخطاء

رسائل خطأ ودّية موحَّدة (نفس نمط Prompt 06، القسم 19)، مع تمييز واضح بين "خطأ شبكة (سيُعاد المحاولة تلقائيًا)" و"خطأ في البيانات (يتطلب تصحيح من المستخدم)".

## 31. استراتيجية التسجيل وتقارير الأعطال

أداة Crash Reporting قياسية (مثل Firebase Crashlytics أو ما يعادلها)، لرصد أعطال ميدانية لا تظهر في بيئة التطوير.

## 32. استراتيجية التحليلات

استخدام أساسي (فتح تطبيق، إكمال مهمة حضور) لأغراض تحسين تجربة الاستخدام، لا تحليلات تسويقية متقدمة في النسخة الأولى.

## 33. استراتيجية تكامل AI

نفس بوابة AI المشتركة المعرَّفة خلفيًا (Prompt 07)، مُستهلكة عبر نفس عقد API — لا منطق AI منفَّذ محليًا على الجهاز في هذه المرحلة.

## 34. استراتيجية التوسع المستقبلي

النواة المشتركة (Section 6) مصمَّمة لتُستهلك من تطبيقات موبايل مستقبلية لقطاعات أخرى (Tourism مستقبلاً)، دون افتراض أي منطق خاص بـ Education داخلها.

## التطبيقات الستة — نظرة معمارية

### 1. تطبيق الطالب (Student App)

**الغرض**: اطلاع ذاتي سريع. **المستخدم المستهدف**: Student. **الوحدات الرئيسية**: الجدول، النتائج، الحضور الشخصي، الفواتير (اطلاع)، الإشعارات. **لوحة رئيسية**: ملخص اليوم (حصص، واجبات إن وُجدت). **سلوك دون اتصال**: اطلاع فقط على آخر بيانات مُزامنة، لا كتابة. **إشعارات دفع**: نتيجة جديدة، تذكير حصة، إعلان عام.

### 2. تطبيق الولي (Parent App)

**الغرض**: متابعة الأبناء والتواصل مع المؤسسة. **الوحدات الرئيسية**: ملفات الأبناء (متعدد)، الحضور، النتائج، الفواتير والأداء الإلكتروني، التواصل المباشر مع الإدارة. **إشعارات دفع ذات أولوية قصوى**: غياب فوري (Prompt 02، قصة مستخدم بأولوية عالية).

### 3. تطبيق الأستاذ (Teacher App)

**الغرض**: الأداة الميدانية الأكثر استخدامًا يوميًا. **الوحدات الرئيسية**: حصصي اليوم، تسجيل حضور (دون اتصال، أولوية قصوى)، إدخال نتائج، رسالة سريعة لولي. **إجراءات سريعة**: "بدء تسجيل الحضور" كإجراء بضغطة واحدة من الشاشة الرئيسية.

### 4. تطبيق الموظف الإداري (Staff App)

**الغرض**: مهام إدارية ميدانية خفيفة (قبول سريع، رد على استفسار Lead). أولوية بناء أقل من الثلاثة أعلاه — يمكن تأجيله لمرحلة لاحقة دون التأثير على القيمة الجوهرية للمنصة.

### 5. تطبيق مدير المؤسسة (Institution Admin App)

**الغرض**: رؤية تنفيذية سريعة أثناء التنقل (لوحة قيادة مبسَّطة، تنبيهات مالية/أكاديمية حرجة). ليس بديلاً عن الويب للمهام الإدارية العميقة، بل مكمِّل سريع.

### 6. تطبيق المشرف العام (Super Admin App)

**الغرض**: مراقبة صحة المنصة عبر كل المؤسسات (مستوى SmartCity، لا خاص بـ Education وحدها). أولوية بناء منخفضة جدًا — يُبنى إن أثبتت الحاجة الفعلية لإدارة عن بُعد خارج لوحة الويب الإدارية.

## عمارة Offline — تفصيل تقني عالي المستوى

- **دخول دون اتصال**: يُسمح باستخدام آخر جلسة صالحة محليًا لفترة محدودة (Grace Period)، لا دخول جديد كامل دون اتصال.
- **حضور دون اتصال**: الأولوية القصوى المطلقة لكامل هذه الوثيقة (Section 11).
- **قائمة انتظار أداءات دون اتصال**: غير موصى بها في النسخة الأولى — العمليات المالية تنتظر اتصالاً فعليًا لتفادي تعارضات حساسة (مطابق لمبدأ Prompt 08، القسم 12: لا تحديثات متفائلة للعمليات المالية).
- **نماذج دون اتصال**: نماذج بسيطة (ملاحظة عن طالب) تُخزَّن محليًا وتُرسل عند الاتصال.
- **رفع وسائط دون اتصال**: مطابق لـ Section 19–20.
- **حل التعارضات**: قاعدة عامة "آخر تحديث فائز" للبيانات غير الحساسة، مراجعة يدوية إلزامية للتعارضات على بيانات حساسة (حضور مسجَّل مرتين بقيم مختلفة من مصدرين).
- **أولوية المزامنة**: العمليات ذات الأثر على الأولياء (حضور) لها أولوية مزامنة أعلى من العمليات الداخلية البحتة.
- **استراتيجية إعادة المحاولة**: تراجعية (Exponential Backoff) بسيطة، مطابقة لغياب Dead Letter Queue حقيقي (Prompt 07).

## الإشعارات الفورية — استراتيجية شاملة

الحضور والغياب، الفواتير والمدفوعات، نتائج الامتحانات، الواجبات (امتداد مستقبلي محتمل)، الشهادات، الرسائل المباشرة، حملات تسويقية (اختيارية، قابلة لإلغاء الاشتراك)، تنبيهات النظام، إشعارات AI — كل فئة تحمل أولوية عرض مختلفة (الحضور/الفواتير أعلى إلحاحًا بصريًا من الحملات التسويقية).

## تجربة الذكاء الاصطناعي على الموبايل

مساعد نصي مبسّط، مساعد صوتي كامتداد مستقبلي بعيد، تقارير وتوصيات ذكية معروضة كبطاقات قابلة للتمرير، بحث ذكي أساسي — كلها استهلاك خفيف لنفس بوابة AI الخلفية، لا منطق مستقل على الموبايل.

## الأمان — إحالة

مطابقة كاملة لـ Prompt 10، مع بنود خاصة بالموبايل تُفصَّل هناك: تخزين آمن للتوكن، تسجيل/إلغاء تسجيل الجهاز (Device Registration/Revocation)، جاهزية القفل ببصمة، جاهزية Certificate Pinning، استجابة لفقدان الجهاز.

## معايير الجودة

أداء (سرعة إقلاع، استجابة تسجيل حضور دون تأخر ملحوظ حتى بشبكة ضعيفة)، قابلية صيانة (نواة مشتركة موحَّدة عبر التطبيقات الستة)، قابلية توسع (بنية تصلح لقطاعات مستقبلية)، إمكانية وصول، RTL، جاهزية اختبار، جاهزية للنشر على المتاجر (App Store/Play Store) بمتطلباتهما القياسية (سياسة خصوصية، أذونات واضحة المبرر).

---

**حالة الوثيقة**: جاهزة للمراجعة. الأولوية المعمارية الأهم: **Offline-first لتسجيل الحضور تحديدًا**، وهي النقطة التي أحالت إليها كل الوثائق السابقة. أولوية بناء التطبيقات الستة الموصى بها: Teacher App وParent App أولاً (أعلى قيمة يومية)، ثم Student App، ثم Admin App، ثم Staff App وSuper Admin App كامتداد لاحق. لا يبدأ العمل على Prompt 10 (Security Architecture) إلا بعد اعتماد هذه الوثيقة أو تسجيل التعديلات المطلوبة عليها.
