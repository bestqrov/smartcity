# العمارة الخلفية وعقود الـ API لقطاع التعليم

> تبني هذه الوثيقة مباشرة على القرارات المثبَّتة سابقًا: `education-service` خدمة NestJS مستقلة (Prompt 03)، عزل منطقي بـ `tenantId` (Prompt 04)، مصادقة عبر `user-service` (Prompt 03، القسم 14). لا تُعاد هنا مناقشة هذه القرارات، بل تُترجم إلى بنية خلفية وعقود API عليا.

---

## 1. فلسفة الخلفية

`education-service` تُبنى **حرفيًا على نفس نمط `tourism-service` الحالي** (نفس بنية المجلدات، نفس نمط الوحدات NestJS، نفس نمط Guards/Strategies) — هذا قرار مقصود لتقليل العبء المعرفي على فريق صغير يعرف Tourism بالفعل. لا ابتكار معماري لأجل الابتكار.

## 2. استراتيجية Clean Architecture

فصل واضح بين: Controller (استقبال/تفويض) → Service (منطق تجاري) → Repository (وصول بيانات عبر Prisma) → Domain Events (نشر أحداث)، مطابق لما حُدِّد في Prompt 03 (القسم 4).

## 3. استراتيجية Domain-Driven Design

كل وحدة وظيفية جوهرية (Prompt 05) = وحدة NestJS مستقلة (Module) بحدود واضحة: `students`, `parents`, `teachers`, `academic` (programs/courses/groups/timetable)، `attendance`, `exams`, `certificates`, `finance` (invoices/payments), `hr` (contracts/payroll), `crm`, `communication`, `documents`.

## 4. السياقات المحدودة

مطابقة لـ Prompt 03 (القسم 6): سياق Education منفصل تمامًا، يلتقي فقط بسياق Identity المشترك.

## 5. الوحدات النطاقية (Domain Modules)

قائمة الوحدات NestJS المقترحة (كل واحدة = مجلد `src/<module>` داخل `education-service`، بنفس نمط `tourism-service/src/hotels`، `src/bookings`...):

`students`, `parents`, `teachers-staff`, `hr` (contracts, payroll), `academic-structure` (programs, subjects, levels, groups), `timetable`, `attendance`, `exams-grades`, `certificates`, `finance` (invoices, payments, scholarships, expenses), `crm-leads`, `communication`, `documents`, `settings`, `analytics-reports`, `audit`.

## 6. الوحدات المشتركة (Shared Modules) داخل الخدمة نفسها

`common` (فلاتر استثناءات، Interceptors موحَّدة لصيغة `IApiResponse`)، `auth` (Guards/Strategy محلية تتحقق من JWT الصادر عن `user-service`، بنفس نمط `tourism-service/src/auth`)، `prisma` (خدمة اتصال Prisma، بنفس نمط `tourism-service/src/common/prisma.service.ts`).

## 7. وحدات البنية التحتية (Infrastructure Modules)

اتصال Prisma، اتصال Redis (تخزين مؤقت + احتمال استخدامه لاحقًا لقفل عمليات حسّاسة كتوليد كشف رواتب)، عميل HTTP داخلي للتواصل مع `user-service` عند الحاجة (تحقق إضافي من بيانات مستخدم).

## 8. الوحدات الأساسية (Core Modules)

`auth` (محلي)، `tenant-context` (استخراج وفرض `tenantId` من التوكن في كل طلب — هذه الوحدة هي خط الدفاع الأول لعزل المستأجرين على مستوى الكود، Prompt 04 القسم 3).

## 9. قواعد التبعية (Dependency Rules)

اتجاه تبعية واحد إلزامي: Controller → Service → Repository. لا Service يستدعي Controller آخر مباشرة؛ التواصل بين وحدات داخلية عبر حقن خدمة (Service Injection) موثَّق، لا استدعاء HTTP داخلي بين وحدات نفس الخدمة.

## 10. استراتيجية تواصل الوحدات

مطابقة لـ Prompt 03 (القسم 9): متزامن داخل الخدمة (حقن خدمات)، غير متزامن عبر أحداث داخلية (In-process Events) بين وحدات الخدمة نفسها (مثال: وحدة `academic-structure` تُصدر حدث "تسجيل جديد"، وحدة `finance` تستمع وتُصدر فاتورة).

## 11. الجاهزية للـ Event-Driven

مطابقة لـ Prompt 03 (القسم 10): NestJS EventEmitter داخليًا فقط في هذه المرحلة، بلا Message Broker خارجي.

## 12. جاهزية CQRS

غير مطلوبة في النسخة الأولى (تعقيد غير مبرَّر لحجم الاستخدام الحالي)؛ الفصل بين القراءة والكتابة يبقى منطقيًا (خدمات مختلفة لأغراض مختلفة) لا بنيويًا صارمًا (لا Event Sourcing، لا قواعد بيانات قراءة منفصلة الآن). يُعاد التقييم عند إثبات حاجة فعلية (Prompt 03، القسم 40).

## 13. استراتيجية طبقة المستودع (Repository Strategy)

كل وحدة تملك طبقة وصول بيانات خاصة بها فوق Prisma Client المشترك، **تفرض `tenantId` برمجيًا في كل استعلام دون استثناء** (Prompt 04، القسم 3) — هذه الطبقة هي التطبيق التقني الفعلي لمبدأ "لا استعلام بدون سياق مستأجر" المثبَّت معماريًا سابقًا.

## 14. استراتيجية طبقة الخدمة

كل خدمة (Service) تحمل منطقًا تجاريًا واحدًا واضح الحدود (مثال: `InvoiceService` لا يحتوي منطق حساب النتائج الأكاديمية).

## 15. استراتيجية التحقق (Validation)

DTO Validation عبر NestJS Pipes (`class-validator`)، بنفس أداة ونمط `tourism-service` الحالي، لكل طلب وارد قبل وصوله لطبقة الخدمة.

## 16. استراتيجية معالجة الأخطاء

Exception Filter موحَّد على مستوى الخدمة يحوّل كل خطأ لصيغة `IApiError` القياسية من `@smartcity/types`، متّسقة مع الصيغة المستعملة حاليًا عبر المنظومة.

## 17–18. استراتيجيتا التسجيل والمراقبة

مطابقة لـ Prompt 03 (القسم 19–20): نفس أداة/نمط `tourism-service`، مع وسم `service: education-service`.

## 19. استراتيجية المهام الخلفية

`@nestjs/schedule` لمهام دورية (تصنيف متأخرات، تذكيرات، فحص عقود)، مطابقة لـ Prompt 03 (القسم 12) — بلا queue خارجي في هذه المرحلة.

## 20. استراتيجية الإشعارات

مطابقة لـ Prompt 03 (القسم 13): نداء REST لـ `notification-service` إن كانت جاهزة فعليًا عند التنفيذ، وإلا مسار مبسّط داخلي قابل للاستبدال لاحقًا دون تغيير واجهة الاستهلاك.

## 21. استراتيجية البحث

استعلامات Prisma/MongoDB أساسية بفهرسة نصية (Prompt 04، القسم 22) في النسخة الأولى.

## 22. استراتيجية تكامل AI

استهلاك بوابة AI مشتركة على مستوى SmartCity إن وُجدت (Prompt 03، القسم 26)، أو بناء طبقة تجريد بسيطة داخل `education-service` (Provider Abstraction محلية) قابلة للاستبدال لاحقًا ببوابة مشتركة دون كسر واجهة الاستهلاك — نفس مبدأ "واجهة ثابتة، تنفيذ داخلي قابل للاستبدال" المستعمل في قرار الإشعارات.

## 23–24. استراتيجيتا التقارير والتحليلات

محرك تقارير داخلي (توليد PDF/Excel) ضمن وحدة `analytics-reports`، قراءة مباشرة من قاعدة البيانات المشتركة مقيَّدة بـ `tenantId`، بدون مستودع بيانات منفصل (Prompt 04، القسم 37–39).

## 25. استراتيجية تخزين الملفات

مطابقة لـ Prompt 03 (القسم 23): يُتحقق من وجود حل تخزين مشترك على مستوى SmartCity عند التنفيذ الفعلي، `education-service` تستهلكه عبر واجهة تجريد داخلية (`StorageService`) لا تستدعي مزوّد التخزين مباشرة من كل وحدة.

## 26. استراتيجية النسخ الاحتياطي

مطابقة لـ Prompt 03/04: نفس سياسة قاعدة البيانات المشتركة، لا سياسة منفصلة.

## 27. استراتيجية التخزين المؤقت

Redis بـ namespace `education:*` (Prompt 03، القسم 22)، لعمليات قراءة كثيفة فقط (لوحات قيادة، جداول)، أبدًا للكتابات المالية.

## 28–30. استراتيجيات الأداء وقابلية التوسع والأمان

مطابقة لـ Prompt 03 (القسم 32–36): توسع أفقي مستقل عبر Docker، أمان مُحال بالكامل لـ Prompt 10.

## لكل وحدة نطاقية — نمط التوثيق (يُطبَّق فعليًا عند التنفيذ لكل وحدة من القسم 5)

الغرض، المسؤوليات، التبعيات، الخدمات العامة المعروضة، الخدمات الداخلية، الأحداث المنشورة، الأحداث المستهلَكة، المهام المجدولة، الصلاحيات المطلوبة، قواعد الأمان، قواعد التحقق، الإعداد، الامتدادات المستقبلية — إطار موحَّد يُملأ لكل وحدة من القسم 5 عند بدء تنفيذها الفعلي، بدل تكراره نظريًا 15 مرة هنا بلا محتوى فعلي جديد.

## عقود API — المبادئ العليا (بلا تنفيذ)

لكل وحدة نطاقية، عقود API تتبع نفس اصطلاحات `tourism-service`/`gateway` الحالية:

- **اصطلاح التسمية**: مسارات REST جمعية (`/api/students`, `/api/invoices`, `/api/attendance`)، مطابقة لنمط `/api/hotels`, `/api/bookings` الحالي.
- **متطلب المصادقة**: كل مسار Education (باستثناء لا شيء — لا مسار عام مجهول الهوية) يتطلب JWT صادر عن `user-service`، محقَّق عبر Guard محلي في `education-service` (Prompt 03، القسم 15).
- **متطلب التفويض**: كل مسار يحدد صراحة الأدوار المسموح لها (مثال: إصدار فاتورة يتطلب `finance_manager` أو أعلى، Prompt 01 القسم 8).
- **صيغة الاستجابة**: موحَّدة عبر `IApiResponse<T>`/`IPaginatedResponse<T>` من `@smartcity/types`، بلا صيغة مخصصة لـ Education.
- **قواعد الترقيم والفلترة والفرز والبحث**: موحَّدة عبر `IPaginationQuery` المشترك.
- **دعم الاستيراد/التصدير**: على مستوى المسارات التي تحتاجه فعليًا (طلبة، فواتير، نتائج)، بمعاينة قبل تأكيد (Prompt 04، القسم 28).
- **العمليات المجمَّعة**: مسارات `bulk` منفصلة عن المسارات الفردية حيث يلزم (استيراد طلبة، ترحيل سنة).
- **تحديد المعدل (Rate Limiting)**: نفس آلية `ThrottlerModule` المستعملة حاليًا في `gateway`.
- **تسجيل التدقيق**: كل عملية كتابة على مورد حساس (مالي، صلاحيات) تُسجَّل تلقائيًا عبر Interceptor موحَّد، لا استدعاء يدوي متكرر في كل Controller.

### مجموعات المسارات المرجعية (بدون تفاصيل تنفيذية)

- إدارة المؤسسة والفروع، الطلبة، الأولياء، الأساتذة/الموظفين، العقود والرواتب، البرامج/المواد/المستويات/الأفواج، الجدول الزمني، الحضور، الامتحانات/التقييمات/النتائج، الشهادات، الفوترة/الأداءات/الأقساط/المنح، النفقات، Leads/CRM، التواصل، المستندات، الإعدادات، التقارير/التحليلات.

كل مجموعة تُضاف كـ entry جديدة صريحة في `routeMap` الحالي لـ `services/gateway` (Prompt 03، فجوة مرصودة رقم 3)، موجَّهة إلى `education-service`.

## عمارة الأحداث (Event Architecture) — مرجع موحَّد

**أحداث نطاقية (Domain Events)**: طالب مسجَّل، فاتورة صادرة، دفعة مستلمة، غياب مسجَّل، نتيجة منشورة، شهادة صادرة (Prompt 03، القسم 11).
**أحداث تكامل (Integration Events)**: مخصصة لتواصل عابر للخدمات مستقبلي (مثلاً إشعار `notification-service`) — تُنفَّذ حاليًا كنداء REST مباشر لا كحدث ناشر حقيقي (Prompt 03، القسم 10).
**أحداث إشعار، تدقيق، دورة حياة، AI**: تُستهلك داخليًا من طرف وحدات `communication`, `audit`, `analytics-reports` بنفس آلية الأحداث الداخلية.
**أحداث الدفع والتسجيل**: أحداث `payment.received`, `enrollment.created` أساسية لتفعيل مسارات مالية وأكاديمية مترابطة (Prompt 04، القسم 26: معاملات).

## المهام الخلفية — مرجع موحَّد

مهام مجدولة (Cron): تصنيف يومي للأقساط المتأخرة، تذكيرات أداء، فحص عقود قاربت الانتهاء، تنظيف بيانات استيراد مؤقتة (Prompt 04، القسم "مجموعات مؤقتة"). سياسة إعادة المحاولة: عدد محاولات محدود مع تسجيل فشل نهائي في سجل تشغيلي قابل للمراجعة اليدوية، بلا Dead Letter Queue حقيقي (لا queue خارجي في هذه المرحلة).

---

## المصادقة — تدفقات مرجعية

مطابقة تمامًا لـ Prompt 03 (القسم 14) و"دورة حياة المصادقة الكاملة": دخول عبر `user-service` عبر gateway، رمز وصول + تجديد، إدارة جلسة عبر Redis (موجودة فعلاً)، استرجاع كلمة مرور عبر `user-service`، دعوة مستخدم جديد بدور Education محدَّد مسبقًا.

## التفويض — مصفوفة عليا

RBAC منفَّذ محليًا داخل `education-service` (Guards)، معايير: المستأجر (`tenantId`)، الفرع (`branchId` عند الاقتضاء)، الدور (Prompt 01، القسم 7–8). لا صلاحية Super Admin افتراضية على بيانات مؤسسة بعينها (Prompt 01، القسم 7.1) إلا بتفويض صريح موثَّق (يُفصَّل أمنيًا في Prompt 10).

## إدارة الملفات — تدفقات مرجعية

رفع (تحقق نوع وحجم الملف قبل التخزين)، تنزيل (تحقق صلاحية الوصول لمالك المستند)، بلا فحص فيروسات فعلي في النسخة الأولى (جاهزية معمارية للإضافة لاحقًا Prompt 10)، بلا معالجة صور متقدمة إلا عند حاجة فعلية.

## الميزات اللحظية (Realtime)

اختيارية في النسخة الأولى — إشعارات "شبه لحظية" عبر تحديث دوري (Polling خفيف) كافية لحجم الاستخدام المتوقع؛ Socket.IO (التوجه التقني العام للمنصة) يُقيَّم فعليًا فقط إن أثبتت لوحة القيادة اللحظية أو الدردشة حاجة واضحة، لا استباقًا.

## بوابة AI الخلفية

طبقة تجريد موحَّدة (نفس مبدأ القسم 22 أعلاه)، مع سياق `tenant + domain=education` صريح في كل نداء لمنع أي تسرّب سياق بين القطاعات (تفصيل أمني كامل في Prompt 10).

## إصدار الـ API

مطابق لـ Prompt 03 (القسم 36): لا نظام Versioning رسمي متقدم حاليًا في المنظومة؛ Education تتبع نفس النمط غير المُصدَر الحالي، مع إبقاء المسارات مصمَّمة بحيث لا تكسر التوافق عند تعديلات بسيطة (حقول إضافية اختيارية لا تُعتبر Breaking Change).

---

**حالة الوثيقة**: جاهزة للمراجعة. الالتزام الأهم فيها: `education-service` تُبنى بنفس نمط `tourism-service` حرفيًا، لتقليل العبء المعرفي على الفريق. لا يبدأ العمل على Prompt 08 (Frontend Architecture) إلا بعد اعتماد هذه الوثيقة أو تسجيل التعديلات المطلوبة عليها.
